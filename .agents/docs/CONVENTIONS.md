# Conventions & Definition of Done

Short, strict rules so any contributor (human or AI) produces consistent code.

---

## Picking up a feature

1. Read `ARCHITECTURE.md` fully, then `CONVENTIONS.md` (this file), then **one** feature
   spec in `features/`. Implement exactly one feature at a time.
2. Do not refactor code outside your feature's file list. Do not "improve" neighbors.
3. If the spec conflicts with reality, stop, add a dated note to `.agents/docs/DECISIONS.md`
   (create the file if missing), and choose the smallest change consistent with
   `ARCHITECTURE.md`.
4. When done, tick the feature's checkbox in `ROADMAP.md` and in the spec header, and
   check every acceptance-criteria box in the spec file.

## Definition of Done (every feature)

- [ ] All spec acceptance criteria are demonstrably met.
- [ ] `npm run lint` — zero errors, zero warnings.
- [ ] `npm run build` — succeeds.
- [ ] `cargo test` (run inside `wasm/`) — passes (Rust features only).
- [ ] No `console.log` left in committed code (debugging output goes through the
      existing logger if one exists, otherwise is removed).
- [ ] No new dependencies without recording them in the feature file's
      **Dependencies added** section (see template) and installing them.
- [ ] TypeScript `strict` stays clean — no `any` unless the spec explicitly allows it.
- [ ] Nothing in `AGENTS.md` or `next.config.ts` changes unless your spec says so.

## TypeScript / React

- Functional components + hooks only. No classes in React code.
- Components in `src/components/**`, pure logic in `src/lib/**` (no React imports there).
- State: React state + contexts (see `SimulationContext`). No Redux/Zustand unless a
  spec adds it.
- All three.js / WASM usage is client-side only: components that mount it must be
  marked `"use client"` and must not run during SSR (guard with `useEffect` or
  `next/dynamic` with `ssr: false` inside a client component — see the bundled guide
  `node_modules/next/dist/docs/01-app/02-guides/lazy-loading.md`).
- Event listeners, rAF loops, observers, WebGL contexts: always dispose on unmount.
- Prefer `readonly` on function parameters that should not mutate; use `const`.
- File naming: React components `PascalCase.tsx`; everything else `camelCase.ts`;
  Rust `snake_case.rs`.

## Rust (wasm crate)

- No `unsafe` unless the ABI pointer exports require it; every `unsafe` block gets a
  comment explaining the safety argument.
- Solver code lives in plain modules with `#[cfg(test)]` unit tests — no
  `wasm_bindgen` inside algorithm modules (thin exports in `lib.rs` only).
- Panics inside exported functions are **forbidden**: return error flags/values
  instead (a panic in WASM poisons the instance). Use `debug_assert!` freely.
- Allocation policy: allocate once in `init_sim`/`set_mesh`; steady-state `step`/advect
  must not allocate.

## Styling / UI

- Tailwind 4 utility classes only; no CSS files beyond `globals.css` theme tokens.
- Dark UI (`bg-neutral-950`-range) with light text; accent palette is the pressure
  colormap (blue → white → red). Keep panels compact; this is a dense instrument UI.
- Units are always displayed next to numbers (`m/s`, `kPa`, `×10⁻⁵ Pa·s`).

## Git

- Conventional Commits: `feat(F006): flood-fill voxelization`, `fix(F010): ...`,
  `docs: ...`. One feature ≈ one commit series; never mix unrelated changes.
- Do not commit `wasm/target/` or `src/wasm/` (both gitignored — see F001).
- Do not touch `AGENTS.md` (auto-generated by `next dev`).

## Testing expectations

- Rust: every algorithm feature (F006–F013) ships unit tests in the same file, per its
  spec's test plan. Numerical tolerances are stated in the spec — use those.
- TS: logic in `src/lib/**` should be importable without React; if the spec lists test
  criteria for it, add a minimal `*.test.ts` using Node's built-in test runner
  (`node --test`) only if the spec asks. No test framework may be added without spec.
- Manual verification steps in specs (visual checks) must actually be performed and
  confirmed in the PR/commit notes.
